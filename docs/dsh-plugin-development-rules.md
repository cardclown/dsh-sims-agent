# DSH 自有插件开发与交付规则

本规则约束自有 DSH 插件：按市场插件模式开发并以上架为交付目标；禁止通过私改第三方包完成集成。

适用于本仓库及从本仓库交付的自有 DSH 插件、适配器、Profile 组合与部署胶水。现有产品逐项补齐，新功能从设计时遵循。纯库和内部辅助文件不需要各自生成市场条目；面向用户独立安装的插件必须有自己的发行与市场交付路径。当前仓库 AGENTS.md 的最短真实链路和无重复审批规则继续有效。

## 1. 开发前先回答四个问题

1. 现有 DSH、已连接插件或市场插件是否已经有可用能力？注明实际版本和公开调用方式。
2. 自有代码究竟负责业务适配、配置组合还是插件自身功能？注明边界与现成复用对象。
3. 用户从市场安装后，如何找到入口、完成配置和使用？不能只给作者服务器的安装脚本。
4. 换一台机器时，包、配置、凭据、状态分别从哪里恢复？不能依靠旧 node_modules 或未归档的开发目录。

在现有任务说明中记录答案，不新增通用注册中心或独立审核系统。

## 2. 上游内部缺陷的标准处理

顺序固定为：记录脱敏证据和影响 → 检查已有 Issue/PR/正式能力 → 准备或经授权提交最小修复需求 → 等待正式发行 → 验证发行内容与行为 → 候选验收 → 按已确认目标切换。

- 上游内部状态和协议由上游负责；自有胶水只消费正式公开契约。不得将“有个内部方法可用”当作公开能力。
- 不私改 node_modules、第三方 src/lib、私有状态文件，不 monkey-patch，不用 `patch-package`、pnpm patchedDependencies、overrides 指向本地改包等方式隐蔽替换上游。
- 普通依赖版本约束或官方支持的配置可以使用，但必须说明来源和目的；不能将它们用作隐藏修改第三方实现的通道。
- 只有用户明确批准精确例外范围时才可能偏离默认边界；报告必须说明修改文件、替代方案、升级影响、制品身份和退出条件。一般的“修好它”“继续”不等于批准私改上游。
- 用户选择等待上游后，不自动改为旧官方版本加人工操作，也不以期限到达当作批准改变功能。正式发布必须包含所需能力，版本号增加、PR 合并和市场提示更新均不足以触发上线。
- 外部反馈采用脱敏错误结构、最小复现和预期行为，不发送真实业务数据、凭据、机器路径或内部源代码。没有发出时明确标记“草稿”，不能称为“已反馈”。

## 3. 等待期与既有本地修订

- 既有可运行修订可按用户选择暂时保留，标记为待退出现场；记录现有版本、原包是否可得、当前影响、冻结内容和正式替代条件，不追认为官方版本。
- 不继续给该修订增加功能，不覆写原包或伪造相同 integrity，不反复在缺失制品的 live Profile 中运行安装修复。
- 自有插件在独立、干净的开发 Profile 中继续开发。对照环境可以采用已发布官方包，但不能因此擅自降级现网。
- 运行树快照只声明实际可支持的同机回退能力。原 tgz 丢失时，原版本可重装仍是未解决项；不得从运行目录重打包后声称找回原制品。
- 修复等待、独立插件开发、市场收录和生产切换分别报告进度，避免一个外部等待扩大为所有开发停工。

## 4. 市场插件的产品形态

- 使用 DSH 的真实 Bundle 元数据、公开配置与宿主扩展接口；实现前阅读当前市场收录说明，并参考能力相近的已上架插件。DSH 与 Codex 插件格式不可混用。
- 自有包具有独立包名、版本、说明、许可证和可获取的发行来源。源码可保留 monorepo 开发，发行物必须脱离作者私有工作区即可安装。
- 正常市场用户完成“安装 → 必要的刷新/重启 → 公开入口配置 → 使用”。初始化有明确需要时可提供插件设置页、宿主公开配置或随包安装入口，但不得要求编辑第三方源码、私有状态或安装树。
- 首选宿主原生资源发现与配置贡献。若缺少公共发现/组合接口，记录缺口并采用明确支持的公开设置入口；若必须改配置文件，须具体说明用户操作并验证升级/卸载保持一致，不能称为一键即用。
- 空 Bundle、资源被打进 tgz、CLI setup 成功均不能单独证明市场安装后可用。市场不会因为包声明了 bin 就自动调用它；不得虚构 install/setup/uninstall hooks。
- 是否需要重启、外部服务、账号、宿主权限或特定平台必须在插件说明中明确。不支持的环境准确显示原因，不要求改共享环境才能掩盖问题。

## 5. 插件管理自身环境的边界

| 内容 | 所有者与要求 |
|---|---|
| 代码、Persona、Preset、Skill、静态资源 | 插件随包携带并用公开包解析或 import.meta.url 定位 |
| 配置 | 使用宿主公开配置入口；保留用户和其他插件设置，默认值不绑定作者站点 |
| 凭据 | 使用宿主凭据机制或受保护引用；不写入源码、tgz、公开目录或日志 |
| 私有状态 | 由插件在宿主允许位置初始化、识别版本、迁移和清理；卸载默认保留有价值数据 |
| Node/pnpm、共享依赖、账号与系统权限 | 由宿主或薄部署入口准备，插件不得修改全局 store 或其他插件的依赖 |
| 跨机恢复 | 部署负责完整发行材料与一致状态转移，插件提供自身状态和兼容说明 |

正式包禁止依赖作者机器的绝对 `file:`、开发 `link:`、无法获取的私有工作区路径；离线材料可使用随交付物携带的相对 tgz。包管理器正常生成的符号链接不等于违规开发链接。无状态插件明确声明无状态，不为统一形式制造数据库或迁移系统。

配置组合不得覆盖整个共享配置而丢失其他插件贡献。公共配置只能整段替换时，要有可验证的组合或配置方案，保留 default、roots、表达式、顺序和权限字段；遇到同名冲突明确报告。

## 6. 发行与市场上架

- 包内 metadata、发行来源和目录条目按当前 DSH 市场规则准备；市场硬要求与本项目附加要求分别注明。
- 固定“源码提交 → 构建 → 包版本 → 原 tgz 摘要”的对应关系；内容变化提升自有版本，不覆盖同版本制品，不挪用第三方身份。
- 采用公开 npm 包作为本项目首选正式发行来源；市场允许的其他来源需能被陌生机器实际安装、更新和追溯。不能把私有 monorepo 整体公开作为快捷操作；只发布已确认可公开的插件源码和资源。
- 发布包、提交目录收录、市场可见、市场安装成功是四项独立证据。目录 PR 未合并或只有公开源码时，不能标记已上架。
- 更新功能复用宿主/市场公开能力；检查 capabilities 与兼容范围，不复制市场内部安装算法，不绑定私有响应字段。
- 完成一次市场真实安装和配置使用，再验证升级、卸载/重装、其他插件共存。最终收录受市场维护者控制，不能预先保证审核时间或结果。

## 7. 安装、迁移与回退

- 将 runtime 与 Profile 的完整锁文件、直接/传递依赖、目标平台和实际安装资源一起保存。清单从真实材料生成，不再靠手写 `/opt` 复制列表维持完整性。
- 目标机使用正确运行账号和独立 store 重新安装；不复制旧 `.modules.yaml` 当作迁移，不手改 storeDir 消除报错，不把 root 安装结果遗留给普通服务用户。
- 候选安装与验证先于线上切换；固定最终目录，安装后不随意移动。正式切换只有一个消息/任务写入者。
- 配置、凭据、业务状态与代码分别备份和恢复；市场设置备份不等于完整离线制品。
- 回退验证旧代码读取新状态的能力，保留已发生业务结果及通知去重记录。不能盲目恢复旧 outbox 导致重复发送。
- 用换 HOME/目录、旧路径不可访问、缺包和摘要错误演练验证本次交付。只在已验证的系统和版本组合内声明可迁移。

## 8. 现有发布流程中的最小检查

1. 代码归属：变更只在自有包与公开契约胶水；检查依赖来源、打包脚本及最终制品，不能只检查 core/plugins 目录。
2. 安装来源：每个包都有可获取原制品或已确认源码发行链，版本与内容对应。
3. 用户链路：从干净 Profile 按市场用户路径安装、配置、使用；无需作者工作区或手改第三方。
4. 升级与退出：兼容声明、配置保留、状态迁移、卸载/重装和回退与实际行为一致。
5. 迁移材料：能从完整材料在新路径重建；故意缺包在切换前失败。

检查并入现有测试、打包和发布步骤。对文档或可逆小改动只做相称验证，不新增独立安全审查、重复审批或无关全量测试。

交付报告保留既有 CODE_READY、DEPLOYED、BUSINESS_VERIFIED 等状态，同时分别列出：公开制品链接、目录收录链接、市场安装结果、真实业务、迁移、回退、Git 提交/推送。未完成项不得由其他层的成功替代。

## 9. 本次纠正的执行入口

DSH 市场当前投稿入口为 [社区目录贡献指南](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin/blob/5599809cf0e63ef2249d923c805c134d6b73e9ca/contributing.md)。条目位于 data/plugins；公开 monorepo 子包可独立收录。字段校验、仓库成熟度与审核要求以投稿时官方规则为准。本项目要求明确许可证、完整材料和迁移验证，不将这些附加标准写成市场强制指定 MIT 或强制 npm。



## 用户模板型插件

- 通过公开创作接口显式导入；同标识拒绝覆盖，升级用新标识保留旧副本。不得覆盖共享 default/roots 来注册插件。
- 模板副本是用户资产，直接卸载代码时保留并准确呈现不可用状态；提供显式移除及原生管理入口说明。修改过的模板不得由插件静默删除。
- 创建记录、模板目录、配置与凭据分别管理；记录不保存作者绝对路径。迁移验证必须包含更换目录后读取原记录、模板识别及显式移除，缺少记录时不猜测所有权。
- 包结构检查与市场收录、页面使用、升级卸载、离线重建分开记录。已有公开接口可解决的问题通过最小自有胶水实现，不保留无条件等待上游的发布阻断。

## 离线重建补充验证

- 宿主 runtime、Profile 分别锁定完整依赖，固定经验证的 peer 组合；只锁顶层宿主版本不能避免传递依赖漂移。SIMS 0.1.2 现场已验证 React/react-dom 同为 18.3.1。
- 保存原始 file 制品、包管理器、平台工具链与缓存；校验缺包/篡改失败后不得继续激活。离线验收须禁止容器网络，并保留实际安装脚本允许配置，不能用跳过脚本代替正常安装验证。
- 在实际目标 CPU 架构执行；模拟执行需明确标记。宿主集成验收使用真实启动入口，避免底层测试遗漏宿主公开配置后误改插件依赖。
